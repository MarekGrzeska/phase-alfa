Pliki testowe .test.ts w apps/web nigdy się nie uruchamiają

istotny

web/apps/web/vitest.config.ts · test.include

Konfiguracja vitesta w apps/web wpuszcza wyłącznie pliki o rozszerzeniu .test.tsx. Plik .test.ts — czyli naturalny wybór dla testu funkcji pomocniczej, która nie rysuje żadnego komponentu — nie jest uruchamiany ani zgłaszany. Vitest nie mówi „pominięto”; po prostu go nie widzi.

Dlaczego to jest problem: taki plik wygląda w repozytorium dokładnie jak każdy inny test, przechodzi przegląd i wchodzi do main, a suite pozostaje zielony. To ten sam gatunek błędu, który CLAUDE.md opisuje w sekcji „Testy, które nic nie sprawdzają”: test, który zawsze był zielony, jest nieodróżnialny od testu, który nic nie sprawdza. Tutaj jest jeszcze gorzej — on nie jest nawet zielony, on nie istnieje.

Sprawdzone przebiegiem. Do apps/web/test/ trafił plik ignored.test.ts z asercją, która musi paść:

web/apps/web/test/ignored.test.ts — celowo czerwony
import { describe, expect, it } from "vitest";

describe("czy ten plik w ogole sie uruchamia", () => {
  it("celowo czerwony", () => {
    expect("ten test powinien byc uruchomiony").toBe("ale nie jest");
  });
});
$ npx vitest run — w katalogu web/apps/web
Test Files  1 passed (1)      ← plik .test.ts nie został nawet policzony
     Tests  3 passed (3)      ← same testy z App.test.tsx
KOD WYJSCIA: 0                ← czerwony test przeszedł niezauważony

Ta sama pułapka stoi po drugiej stronie: packages/core wpuszcza wyłącznie .test.ts, więc plik .test.tsx byłby tam niewidoczny. Tam jest to mniej prawdopodobne (pakiet nie ma prawa dotknąć JSX-a), ale mechanizm jest ten sam.

Jak to naprawić

Najprościej — objąć oba rozszerzenia w obu pakietach: 

// web/apps/web/vitest.config.ts
include: ["test/**/*.test.{ts,tsx}"],

// web/packages/core/vitest.config.ts
include: ["test/**/*.test.{ts,tsx}"],

Wariant mocniejszy: skasować include w ogóle i zostawić domyślny wzorzec vitesta (**/*.{test,spec}.?(c|m)[jt]s?(x)), który obejmuje wszystkie sensowne rozszerzenia. Wtedy nie ma czego przeoczyć przy dokładaniu kolejnego.

Niezależnie od wariantu warto powtórzyć powyższy przebieg z celowo czerwonym plikiem .test.ts — poprawka ma być widziana na czerwono, tak jak trzy warstwy zero-DOM.

2

task dev obiecuje port 5173, a Vite po cichu bierze inny

istotny

Taskfile.yml:183 · zadanie dev

Komunikat wypisywany przy starcie ma numer portu weba wpisany na sztywno:

Taskfile.yml:183
- cmd: 'echo "API: http://localhost:${API_PORT:-5014} · web: http://localhost:5173 (proxy /api → API)"'

Vite domyślnie nie upiera się przy porcie 5173: gdy jest zajęty, wypisuje jedną linijkę i wstaje na następnym wolnym. Deweloper, który ma tam już coś innego (drugie repozytorium, poprzedni task dev, który nie zdążył się zamknąć), dostaje komunikat wskazujący adres, pod którym nic nie stoi — i zaczyna szukać błędu w proxy albo w API, choć oba są sprawne.

To jest dokładnie ta klasa błędu, którą repozytorium już raz naprawiło — i to opisało w komentarzu kilka linijek wyżej w tym samym pliku, przy okazji API_PORT: „Stal wczesniej na sztywno w trzech plikach WERSJONOWANYCH naraz […] wiec deweloper z zajetym 5014 nie mial gdzie go zmienic bez edycji repozytorium”. Port weba wrócił tą samą drogą.

Sprawdzone przebiegiem — dwa serwery Vite obok siebie:

$ npx vite --port 5173, a potem drugi npx vite w tym samym katalogu
Port 5173 is in use, trying another one...
  ➜  Local:   http://localhost:5174/     ← pierwszy serwer

Port 5173 is in use, trying another one...
Port 5174 is in use, trying another one...
  ➜  Local:   http://localhost:5175/     ← drugi serwer

Taskfile przez cały czas obiecuje: http://localhost:5173
Jak to naprawić

Dwie drogi, obie dobre — wybór zależy od tego, czy port weba ma być konfigurowalny.

Głośna porażka — strictPort sprawia, że Vite nie zgaduje, tylko przerywa z komunikatem. Komunikat z Taskfile'a przestaje móc skłamać: 

// web/apps/web/vite.config.ts
server: {
  port: Number(env.WEB_PORT ?? 5173),
  strictPort: true,
  proxy: { /* … */ },
}

Port z konfiguracji — WEB_PORT w .env i .env.example, obok DB_PORT, API_PORT i BLOB_PORT, a w Taskfile ${WEB_PORT:-5173}. Wtedy jedna wartość rządzi serwerem i komunikatem naraz — tak samo jak przy API.

Manifest PWA bez ikon — aplikacji nie da się zainstalować

drobny

web/apps/web/vite.config.ts · sekcja manifest

Manifest deklaruje nazwę, kolory i display: "standalone", ale nie ma w nim icons. Przeglądarki traktują ikony jako wymagane: bez nich nie pokazują propozycji instalacji i nie dodają aplikacji do ekranu głównego.

Dlaczego warto o tym wiedzieć teraz: build kończy się komunikatem, który wygląda na pełen sukces, i nic nie mówi o brakującym elemencie. Ktoś, kto w W4 sięgnie po „zainstaluj aplikację”, nie zobaczy żadnego błędu — po prostu opcji nie będzie.

$ cat web/apps/web/dist/manifest.webmanifest
{"name":"Klucz","short_name":"Klucz","description":"Ocenianie odpowiedzi według zasad
oceniania CKE","start_url":"/","display":"standalone","background_color":"#ffffff",
"theme_color":"#1f2933","lang":"pl","scope":"/"}
                                            ← brak klucza "icons"

Stopień jest drobny, bo plan G1.4.1 nie obiecuje instalowalności — mówi tylko „PWA jako plugin”, a alfa jest POC-em na jednym komputerze. Ale web/README.md i opis commita mówią „PWA”, więc warto, żeby to słowo miało pokrycie albo zastrzeżenie.

Jak to naprawić

Dwie ikony w public/ (192 i 512 pikseli) plus wpis w manifeście: 

manifest: {
  // …
  icons: [
    { src: "/icon-192.png", sizes: "192x192", type: "image/png" },
    { src: "/icon-512.png", sizes: "512x512", type: "image/png" },
    { src: "/icon-512.png", sizes: "512x512", type: "image/png", purpose: "maskable" },
  ],
}

Albo — jeśli instalowalność ma poczekać na W4 — jedno zdanie w web/README.md: „manifest jest bez ikon, więc aplikacja nie jest jeszcze instalowalna; ikony wchodzą razem z…”. Zapisane zastrzeżenie kosztuje mniej niż pół godziny szukania, dlaczego przeglądarka milczy.

„packages/core buduje się osobno” sprawdza wyłącznie CI

drobny

Taskfile.yml:120 · zadanie test:web

Plan G1.4.1 kończy się zdaniem „Zrobione, gdy: task dev podnosi web z HMR, packages/core buduje się osobno”. Budowanie osobno sprawdza w tym branchu tylko zadanie web w CI (pnpm -C web -r build). Lokalne task test:web uruchamia typecheck i vitest, ale nie build.

Różnica nie jest teoretyczna: tsconfig.build.json włącza declaration: true, a emisja deklaracji potrafi paść tam, gdzie --noEmit przechodzi (klasyczny przypadek to typ, którego nie da się nazwać w pliku .d.ts). Skutek dla autora: task test na zielono, push, i czerwone CI z błędu, którego lokalnie nie dało się zobaczyć.

Stopień jest drobny, bo CLAUDE.md wprost stawia CI jako jedyne źródło prawdy o zielonym buildzie, a opis zadania („Typecheck (w tym zero-DOM) + vitest”) mówi uczciwie, czego nie robi. To niedomknięcie pętli, nie kłamstwo.

Jak to naprawić 
test:web:
  desc: Typecheck (w tym zero-DOM) + vitest + build
  cmds:
    - cmd: |
        if test -f web/pnpm-workspace.yaml; then
          pnpm -C web -r typecheck
          pnpm -C web -r test
          pnpm -C web -r build
        else
          echo "POMIJAM test:web — brak workspace (wchodzi w G1.3.2)"
        fi

Koszt to około sekunda dla core i sekunda dla apps/web. Przy okazji warto poprawić gałąź else: mówi „wchodzi w G1.3.2”, a G1.3.2 dawno weszło — komunikat myli następną osobę.

Lista zakazanych zależności gubi @types/react-dom i inne frameworki

drobny

web/packages/core/test/zero-dom.test.ts · stała FORBIDDEN

Lista wymienia react, react-dom, @types/react, jsdom, mathlive i kilka innych — ale nie @types/react-dom, ani żadnego frameworka spoza rodziny Reacta (preact, solid-js, vue, svelte).

Ryzyko jest umiarkowane, bo to druga warstwa ochrony: gdyby ktoś dołożył preact i faktycznie go użył, warstwa pierwsza (tsconfig) zapali się na pierwszym dotknięciu DOM-u. Luka dotyczy okna między dopisaniem zależności a jej użyciem — czyli dokładnie tego, po co ta warstwa powstała.

const FORBIDDEN = [

  "mathlive", "jsdom", "happy-dom",
  "@vitejs/plugin-react", "@testing-library/react", "@testing-library/dom",

Wariant, który nie wymaga pilnowania listy: odwrócić regułę i sprawdzać, czy dependencies i peerDependencies są puste. Dziś są, a packages/core z definicji ma nie mieć zależności produkcyjnych — devDependencies zostawić przy liście zakazanych.

TaskKind powiela słownik ze schematu bazy

do rozważenia

web/packages/core/src/session.ts:11

Typ TaskKind wypisuje cztery wartości, które równolegle stoją w więzie CHECK w migracji 0001_corpus.sql:

web/packages/core/src/session.ts oraz ingest/schema/migrations/0001_corpus.sql
export type TaskKind = "closed" | "open_short" | "open_extended" | "essay";
kind text NOT NULL CHECK (kind IN ('closed', 'open_short', 'open_extended', 'essay'))

Dziś obie listy się zgadzają — sprawdziłem. Pytanie jest o jutro: to samo pojęcie ma dwa zapisy w dwóch warstwach, a repozytorium ma na taki układ mocną opinię. CLAUDE.md tłumaczy słownik pojęć raz i wprost pisze, że rozjazd między warstwami sprawia, iż „parser, schemat i moduł C# nazywają tę samą rzecz na trzy sposoby”. Dla kontraktu API rozwiązaniem jest generowany schema.d.ts i bramka dryfu; dla tego słownika nie ma dziś nic.

Do rozważenia, nie do naprawienia teraz: dopóki zadania są wpisane na sztywno w App.tsx, nie ma czego pilnować. Rzecz staje się realna w chwili, gdy zadania zaczną przychodzić z API — bo wtedy schema.d.ts będzie już niósł ten sam typ, wygenerowany.

Propozycja

Gdy endpoint z zadaniami powstanie (A2 albo W2), wziąć kind z wygenerowanego schematu zamiast deklarować go po raz drugi — a jeśli packages/core nie ma zależeć od klienta API, przekazywać typ przez parametr generyczny albo trzymać go w packages/core i to stamtąd sprawdzać zgodność testem, który czyta migrację. Wybór jest autora; ważne, żeby był świadomy, a nie domyślny.

Pole tekstowe pokazuje wartość znormalizowaną przez model

do rozważenia

web/apps/web/src/App.tsx · <input value={answerOf(...) ?? ""}>

answerTask celowo kasuje odpowiedź złożoną z samych białych znaków — i to jest dobra decyzja, opisana w komentarzu i pokryta testem. Ale pole w App.tsx bierze swoją wartość z modelu, więc normalizacja modelu jest natychmiast widoczna w tym, co użytkownik ma przed oczami.

Sprawdzone przebiegiem, sondą w środowisku jsdom:

$ npx vitest run test/probe.test.tsx — sonda, skasowana po pomiarze
po wpisaniu spacji, wartosc pola = ""       ← spacja znika w locie
po wpisaniu ' 5', wartosc pola   = " 5"     ← tu już jest w porządku
po wpisaniu '105 ', wartosc pola = "105 "   ← i tu też

Zasięg jest wąski: znika wyłącznie wpis złożony z samych spacji. Nie ma tu utraty danych ani błędnego wyniku — jest drobna niespójność między tym, co użytkownik wpisał, a tym, co widzi. Przy dzisiejszym szkielecie to bez znaczenia; przy realnym ekranie ucznia w A4, gdzie odpowiedzią bywa wyrażenie matematyczne budowane znak po znaku, warto mieć to rozstrzygnięte świadomie.

Propozycja

Rozdzielić „co użytkownik wpisuje” od „co model uznaje za odpowiedź”: trzymać surowy tekst pola w stanie komponentu, a do answerTask podawać go bez zmian — model dalej normalizuje na swoje potrzeby, a pole pokazuje to, co zostało wpisane. Albo zostawić jak jest i dopisać jedno zdanie w docstringu answerTask, że wartość zwracana przez answerOf nie nadaje się na value kontrolowanego pola.

Typecheck weba liczy się w CI dwa razy

do rozważenia

.github/workflows/ci.yml · zadania web i kontrakt

Oba zadania wołają pnpm -C web -r typecheck, i oba instalują cały workspace weba. Powód jest dobry i zapisany w komentarzu: kontrakt sprawdza klienta wobec świeżo wygenerowanego schema.d.ts, a web wobec tego z repozytorium. To są dwa różne pytania.

Rzecz do rozważenia dotyczy kosztu, nie poprawności. Plan G1.5 ma na ten temat osobne zastrzeżenie: „Repozytorium jest prywatne, więc minuty GitHub Actions liczą się do darmowego limitu konta […] Konsekwencje: cache'ować zależności […] nie odpalać macierzy systemów operacyjnych”. Podwójna instalacja workspace'u i podwójny typecheck to dokładnie ten rachunek.

Propozycja

Trzy możliwości, w kolejności od najmniej inwazyjnej:

  • Zostawić i zmierzyć. Jeśli zadanie web trwa około minuty, rachunek jest do przyjęcia — a wtedy warto tę liczbę zapisać przy G1.5, żeby nikt nie wracał do tematu w domysłach.
  • Zawęzić kontrakt do samego @klucz/api-client (pnpm -C web --filter @klucz/api-client typecheck) — to jedyny pakiet, którego dotyczy pytanie o dryf kontraktu.
  • Scalić zadania, jeśli i tak mają wspólną instalację. Kosztem jest to, że przy czerwonym buildzie widać jedną porażkę zamiast dwóch — a rozróżnienie „zepsuty kontrakt” od „zepsuty web” jest coś warte.

04

Co jest dobre

Rzeczy warte utrzymania przy kolejnych zmianach — nie kurtuazja.

  • Zero-DOM ma cztery warstwy, a nie trzy. Do trzech z planu dochodzi środowisko node w vitest — jeśli ktoś obejdzie typy przez any, document i tak nie istnieje w czasie wykonania. Ta czwarta warstwa nie kosztowała nic i łapie dokładnie to, czego trzy pozostałe nie widzą.
  • Rozdzielenie tsconfiga produktu i testów jest asercją, nie umową. Test zero-DOM sprawdza nie tylko lib i types, ale też że include to dokładnie ["src"]. Bez tego ktoś mógłby dopisać test do produktu i po cichu wpuścić @types/node do pakietu, który ma być czysty.
  • fileURLToPath zamiast new URL(...).pathname. Na Windows to drugie daje /C:/… i zostawia spacje zakodowane jako %20 — a ścieżka tego repozytorium ma spacje. Komentarz nad tą linijką mówi wprost dlaczego, więc nikt tego nie „uprości” z powrotem.
  • Port API czytany z .env, nie zaszyty. Konfiguracja Vite bierze API_PORT z tego samego pliku, z którego czyta go Taskfile — jedna wartość rządzi proxy i komunikatem API naraz. (Szkoda, że port weba poszedł inną drogą — komentarz 2.)
  • Sekrety nie wyciekają do bundla mimo loadEnv(mode, root, ""). Pusty prefiks wczytuje po stronie Node'a wszystko z .env, łącznie z DB_PASSWORD. Sprawdziłem zbudowany dist/: hasła tam nie ma, bo o tym, co trafia do przeglądarki, decyduje envPrefix, a ten został domyślny. Rzecz działa poprawnie — ale warto o niej wiedzieć, zanim ktoś zmieni envPrefix.
