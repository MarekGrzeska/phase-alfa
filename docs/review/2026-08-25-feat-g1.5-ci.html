1

README obiecuje ochronę main, której GitHub na tym planie nie udostępnia

istotny

README.md:116 · sekcja „CI"

Ostatnie zdanie nowej sekcji o CI brzmi: „Gałąź main jest chroniona: merge dopiero po przejściu wszystkich czterech zadań". Ochrona nie została włączona — i nie chodzi tylko o to, że autor odłożył decyzję. GitHub jej tutaj nie da: ochrona gałęzi w repozytorium prywatnym wymaga planu Pro.

$ gh api repos/MarekGrzeska/phase-alfa/branches/main/protection
{"message":"Upgrade to GitHub Pro or make this repository public to enable
this feature.","status":"403"}          ← nie „nie wlaczono", tylko „nie mozna"

Dlaczego to jest problem: README jest instrukcją dla następnej osoby i dla autora za pół roku. Zdanie mówi „jest bramka" w miejscu, gdzie bramki nie ma — a czytelnik zachowa się tak, jakby była: wypchnie coś na main w przekonaniu, że cokolwiek go zatrzyma, jeśli testy są czerwone. To ten sam gatunek co test, który zawsze przechodzi: dokument, który zawsze mówi „bezpiecznie".

Jak to naprawić

Zdanie zamienić na stan faktyczny i powiedzieć, co naprawdę pilnuje jakości — czyli PR i cztery zadania, których wynik widać przed scaleniem: 

Ochrony galezi NIE MA i na tym planie GitHuba byc nie moze (repozytorium jest
prywatne, ochrona wymaga Pro). Bramka jest wiec dyscyplina, nie ustawieniem:
scalamy przez PR i dopiero z czterema zielonymi checkami.

Ta sama poprawka należy się planowi (komentarz 8): krok 3 w §G1.5 opisuje czynność, której nie da się wykonać.

2

Zadania CI nie mają limitu czasu — jeden zwis to 6 godzin z miesięcznego limitu

istotny

.github/workflows/ci.yml · wszystkie cztery zadania

Żadne z czterech zadań nie ustawia timeout-minutes, więc obowiązuje domyślny limit GitHuba: 360 minut na zadanie. Zawieszony dotnet test, docker pull czekający na sieć albo usługa Postgresa, która nigdy nie zgłosi zdrowia, będą stać sześć godzin i dopiero wtedy zostaną ubite.

Dlaczego to jest problem: repozytorium jest prywatne, więc minuty liczą się do limitu konta (2000/miesiąc na planie Free) — i to jest ten sam rachunek, dla którego w tym samym PR-ze zmieniono wyzwalacz z ['**'] na main. Jeden zwis kasuje 18% budżetu miesięcznego i nie mówi nic, czego nie powiedziałby po dwóch minutach. Zmiana wyzwalacza oszczędza kilka minut na push; brak limitu potrafi oddać kilkaset naraz.

zmierzone czasy zadań (przebieg 32877307223) wobec domyślnego limitu
ruff + pytest + migracje        28s
typecheck (zero-DOM) + vitest   41s
dryf OpenAPI                  1m02s
build + testy backendu        1m06s
domyslny limit GitHuba          360 min   ← okolo 200 razy wiecej niz najdluzsze zadanie
Jak to naprawić

Jedna linijka na zadanie, z zapasem rzędu dziesięciokrotności zmierzonego czasu:

jobs:
  python:
    name: ruff + pytest + migracje
    runs-on: ubuntu-latest
    timeout-minutes: 10

Zapas ma być duży, bo zimny cache i wolniejszy runner to normalne wahania — limit ma łapać zwis, nie gorszy dzień. Dziesięć minut przy zadaniu, które chodzi 28 sekund, spełnia oba warunki.

3

Skrypt dla macOS-a nie ma bitu wykonywalności, a README każe go wołać przez ./

istotny

scripts/dev-stack.sh · README.md, tabela „Cały stos jednym poleceniem"

README podaje dla macOS-a i Linuksa polecenie ./scripts/dev-stack.sh, a plik wszedł do repozytorium z trybem 100644 — czyli bez prawa uruchomienia. Na macOS-ie i Linuksie to polecenie kończy się permission denied zanim cokolwiek się wykona.

$ git ls-files -s scripts/
100644 dcaa103 0  scripts/dev-stack.ps1
100644 b661b09 0  scripts/dev-stack.sh    ← 644, nie 755 — brak prawa uruchomienia

Dlaczego to jest problem: ten skrypt istnieje po to, żeby pierwsze uruchomienie po klonie było jednym poleceniem z README. Na Windows sprawdzian klonu od zera przeszedł (bit wykonywalności nie ma tam znaczenia), więc ścieżki macOS-owej nikt nie widział — a to właśnie ona jest jedyną, do której ten plik służy. Objaw jest przy tym mylący: użytkownik widzi błąd uprawnień i szuka problemu w swoim systemie, nie w repozytorium.

Jak to naprawić 
git update-index --chmod=+x scripts/dev-stack.sh
git commit -m "fix: bit wykonywalnosci na dev-stack.sh"

git update-index --chmod=+x, a nie chmod — na Windows system plików nie niesie tego bitu, więc zmiana musi trafić wprost do indeksu gita. Alternatywa, jeśli bit ma nie być potrzebny: zmienić README na sh scripts/dev-stack.sh — ale wtedy dwie platformy dostają dwie różne konwencje wywołania bez powodu.

4

Backtick w komunikacie zjada słowo „task"

drobny

scripts/dev-stack.ps1:30 · komunikat przy braku go-task

W PowerShellu backtick jest znakiem ucieczki, a `t to tabulator. Komunikat napisany jako "brak `task` — zainstaluj: …" nie pokazuje więc nazwy brakującego narzędzia, tylko tabulator i resztę słowa.

$ powershell -NoProfile -Command '$m = "brak `task` — zainstaluj: winget install Task.Task"; …'
WIDAC: [brak 	ask - zainstaluj: winget install Task.Task]
TAB w srodku: True             ← `t zamienilo sie w tabulator, nazwa narzedzia znikla

Dlaczego to jest problem: to jest pierwszy komunikat, jaki zobaczy ktoś na maszynie bez go-task — czyli w jedynej sytuacji, dla której ta gałąź kodu powstała. Zamiast „brak task" czyta „brak     ask". Reszta zdania ratuje sytuację, ale komunikat diagnostyczny nie powinien wymagać domyślania się.

Jak to naprawić

Apostrofy w środku napisu, dokładnie tak jak w wersji .sh:

Fail "brak 'task' — zainstaluj: winget install Task.Task"
5

Wersja PowerShell kończy się kodem 0, nawet gdy task dev padł

drobny

scripts/dev-stack.ps1 · ostatnia linijka

Skrypt kończy się wywołaniem task dev i niczym więcej. Windows PowerShell nie przenosi kodu wyjścia natywnego programu na kod wyjścia skryptu, więc plik zawsze kończy się zerem. Wersja .sh zachowuje się odwrotnie — set -e i ostatnie polecenie oddają prawdziwy kod.

$ powershell -File tail-exit.ps1 — skrypt konczy sie `cmd /c "exit 3"`
kod wyjscia skryptu PS: 0      ← program zwrocil 3, skrypt raportuje sukces

Dlaczego to jest problem: task dev potrafi paść z powodu, który ten sam PR właśnie wprowadził — strictPort przerywa start Vite, gdy port jest zajęty. Człowiek przy konsoli zobaczy błąd i nic złego się nie stanie; ale dwie wersje tego samego skryptu odpowiadają na to samo pytanie inaczej, a wrapper, który zawsze mówi „sukces", jest dokładnie tym, przed czym ostrzega CLAUDE.md.

Jak to naprawić 
task dev
exit $LASTEXITCODE

Akcje na Node 20 — GitHub ostrzega w każdym przebiegu

Każdy przebieg kończy się ostrzeżeniem: dwie użyte akcje deklarują Node 20, a GitHub uruchamia je na Node 24 wbrew deklaracji.

ostrzeżenie z przebiegu 32878030217
! Node.js 20 is deprecated. The following actions target Node.js 20 but are
  being forced to run on Node.js 24: actions/checkout@v4, actions/setup-dotnet@v4

Dlaczego to jest problem — i kiedy: dziś to sam szum w logu, bo podkładka działa. Ugryzie w dniu, w którym GitHub ją zdejmie: zadania staną na kroku checkout, czyli na pierwszym, i to bez związku ze zmianą, która akurat będzie w PR-ze. Data nie jest ogłoszona, ostrzeżenie chodzi od września 2025.

Jak to naprawić

Podbić obie akcje do @v5 — z jednym sprawdzeniem po drodze: setup-dotnet@v5 musi dalej przyjmować wejścia cache i cache-dependency-path, bo na nich stoi cache NuGeta z tego PR-a. Jeśli nazwy się zmieniły, cache przestanie działać po cichu — bez błędu, tylko z wolniejszym przebiegiem.

Skrypt dla Linuksa podpowiada instalację przez brew

drobny

scripts/dev-stack.sh · komunikat przy braku go-task

Komunikat brzmi brak 'task' — zainstaluj: brew install go-task/tap/go-task, a skrypt obsługuje macOS i Linuksa. Na Linuksie brew zwykle nie istnieje, więc podpowiedź prowadzi do instalowania menedżera pakietów po to, żeby zainstalować jedno narzędzie.

Jak to naprawić

Dołożyć wariant niezależny od systemu — ten sam, który stoi w README:

fail "brak 'task' — zainstaluj: brew install go-task/tap/go-task (macOS)
albo npm i -g @go-task/cli (wszedzie)"

Czym zastąpić bramkę na main, skoro ochrona jest niedostępna

do rozważenia

docs/plan-A1.md §G1.5, krok 3

Plan mówi: „Ochrona gałęzi main: wymagane przejście wszystkich czterech zadań". Tego kroku nie da się dziś wykonać (komentarz 1) — nie dlatego, że go pominięto, tylko dlatego, że GitHub odmawia. Plan opisuje więc czynność niewykonalną, a to myli następną osobę bardziej niż brak wpisu.

Propozycja

Cztery drogi, w kolejności od najtańszej:

  • Skreślić krok i zapisać dlaczego. Plan mówi wtedy prawdę, a dyscyplina zostaje na autorze — przy jednoosobowym repozytorium to uczciwy wybór.
  • Hak pre-push lokalnie. Odrzuca push prosto na main. Pilnuje nawyku, ale nie jest bramką: hak siedzi w .git/, więc nie wchodzi do repozytorium i nie działa na drugiej maszynie, dopóki ktoś go tam nie zainstaluje.
  • Repozytorium publiczne. Ochrona staje się darmowa, a minuty Actions przestają się liczyć do limitu — czyli znika też powód zmiany wyzwalacza z tego PR-a. Kolizji z G0.1 nie ma, bo arkusze CKE i tak nie wchodzą do repozytorium. Decyzja jest jednak szersza niż CI i należy do autora.
  • GitHub Pro. Stały koszt za jedno ustawienie; przy jednej osobie trudno to uzasadnić.

Zmiana samego przeglądu HTML odpala cztery zadania

do rozważenia

.github/workflows/ci.yml · sekcja on

Ten dokument, plany w docs/ i README nie zmieniają żadnego bajtu kodu, a mimo to każdy commit dotykający wyłącznie ich uruchamia cztery zadania — łącznie około trzech i pół minuty. Przy rachunku minut, którym ten PR się zajmuje, to jest pozycja tego samego rzędu co usunięta podwójna instalacja workspace'u.

Zastrzeżenie, przez które to jest „do rozważenia", a nie „drobny": paths-ignore sprawia, że zadanie się nie uruchamia, a nie że kończy się sukcesem. Gdy kiedykolwiek wejdą wymagane checki (komentarz 8), taki PR utknie w stanie „expected — waiting for status", i to bez żadnego komunikatu, który prowadziłby do przyczyny. To pułapka znana i nieprzyjemna.

Propozycja

Jeśli ochrona main ma pozostać niedostępna, paths-ignore na docs/** i **/*.md jest bezpieczne i oszczędza realne minuty. Jeśli kiedyś dojdą wymagane checki — wtedy zamiast paths-ignore stosuje się zadanie-zaślepkę, która zgłasza sukces przy zmianie samej dokumentacji. Do czasu podjęcia decyzji z komentarza 8 lepiej nie ruszać niczego.

BOM w skrypcie .ps1 pilnuje wyłącznie komentarz

do rozważenia

scripts/dev-stack.ps1 · nagłówek pliku

Plik zaczyna się ostrzeżeniem, że musi być zapisany jako UTF-8 z BOM-em — bo bez niego Windows PowerShell 5.1 czyta go jako ANSI i skrypt się rozsypuje. Ostrzeżenie jest prawdziwe i dobrze uzasadnione, ale to komentarz, a nie bramka: edytor, który zapisze plik bez BOM-u, zepsuje skrypt i nikt się o tym nie dowie aż do następnego uruchomienia na Windows. W repozytorium, które zero-DOM pilnuje czterema warstwami, to wyraźny wyjątek.

$ git show HEAD:scripts/dev-stack.ps1 | head -c 3 | od -An -tx1
ef bb bf                       ← BOM przezyl gita — sprawdzone, ale nikt tego nie pilnuje
Propozycja

Trzy bajty da się sprawdzić jednym poleceniem. Miejsce jest kwestią gustu — krok w zadaniu python (jedyne, które nie potrzebuje niczego poza powłoką) albo osobny test: 

test "$(head -c 3 scripts/dev-stack.ps1 | od -An -tx1 | tr -d ' ')" = "efbbbf" ||
  { echo "BRAK BOM: PowerShell 5.1 przeczyta ten plik jako ANSI"; exit 1; }

Wariant tańszy w utrzymaniu, ale słabszy: trzymać w .ps1 polszczyznę bez znaków diakrytycznych. Wtedy plik jest czystym ASCII i BOM przestaje być potrzebny — kosztem zasady 2 z CLAUDE.md.

04

Co jest dobre

Rzeczy warte utrzymania przy kolejnych zmianach — nie kurtuazja.

  • Podwójny przebieg zniknął i widać to w liczbach. Wcześniej jeden push do gałęzi z otwartym PR-em dawał dwa przebiegi po cztery zadania. Po zmianie trzy pushe na tę gałąź dały trzy przebiegi, nie sześć — sprawdzone w gh run list, a nie założone.
  • cancel-in-progress wyłączone na main. Łatwo było wpisać true za planem i skończyć z gałęzią główną, na której część przebiegów jest anulowana bez śladu, co właściwie pokazywały. Wyjątek jest wąski i opisany w komentarzu.
  • Lockfile'e NuGeta domykają zasadę, nie dokładają nowej. Python miał uv sync --frozen, web pnpm install --frozen-lockfile, a backend nie miał nic. Teraz trzy warstwy przywracają zależności tak samo, a NU1004 widziano na czerwono.
  • Sprawdzian klonu od zera złapał dwa realne błędy. I to nie byle jakie: obie pułapki PowerShella 5.1 wyglądały na coś zupełnie innego niż były (zatrzymuje : The term 'zatrzymuje' is not recognized przy błędzie kodowania, „Docker nie odpowiada" przy działającym Dockerze). Bez uruchomienia całej ścieżki żadna z nich nie miała prawa się ujawnić.
  • Obie pułapki wylądowały w CLAUDE.md, nie tylko w commicie. Dotyczą każdego następnego skryptu .ps1, więc miejsce jest właściwe. Wiedza z jednego debugowania została zamieniona w regułę.
  • Skrypty nie powtarzają Taskfile'a. Wołają task i dokładają wyłącznie to, czego Taskfile z definicji nie może: cp .env.example .env (brak cp w interpreterze go-task na Windows) i sprawdzenie, czy silnik Dockera odpowiada, a nie tylko czy jest zainstalowany. Drugie źródło prawdy nie powstało.
  • Komunikat po task up mówi, co dalej. „Kontenery zostają w tle; zatrzymuje je task down" — jedno zdanie, które oszczędza pytanie „dlaczego baza dalej stoi po Ctrl+C".
