Czym jest ten agent i gdzie stoi

granica warstw · localhost · bramka do korpusu

Agent to panel po prawej stronie ekranu korekty i inspektora. Odpowiada na pytania o korpus, tłumaczy jak co działa, przenosi korektora na właściwą stronę narzędzia, poprawia rekordy i uruchamia przebiegi ingestu. Wszystko, co umie, jest narzędziem MCP — nie ma ani jednej zdolności dostępnej tylko z panelu.

Siedzi w ingest/, czyli w warstwie Pythona, i to jest świadome: C# nigdy go nie widzi. Obowiązuje ten sam wyjątek od granicy warstw, którym jest sam ekran korekty — lokalne narzędzie na 127.0.0.1, edytujące rekordy zanim staną się korpusem.

Trzy reguły, na których stoi całość, i które warto mieć w głowie czytając resztę:

  • Zapis do korpusu tylko przez db.save i db.decide — tę samą drogę, którą idzie formularz człowieka i przebieg task verify. Więc status wychodzi z porównania z bazą, więzy odrzucają śmieci agenta tak samo jak śmieci parsera, a dziennik correction_event zapisuje się sam.
  • Trzeci autor rozstrzygnięć ma nazwę w schemacie: task.reviewed_by = 'agent' (migracja 0010, po human i model). Powrót do stanu sprzed agenta to jeden UPDATE, nie archeologia.
  • Zgoda człowieka jest cechą narzędzia, nie logiką panelu. Rozstrzygnięcie, zmiana rekordu już w korpusie, surowy SQL i płatny przebieg wykonują się dopiero po kliknięciu — także wtedy, gdy narzędzie woła Claude Code z terminala.

Jeden rejestr, trzy wejścia

agent w panelu jest klientem MCP jak każdy inny

Dlaczego jeden rejestr, a nie „narzędzia panelu" osobno

agent/server.py

Gdyby panel miał własny zestaw funkcji, a serwer MCP swój, po dwóch tygodniach byłyby to dwa różne zestawy — i żadne z nich nie byłoby przetestowane w obu drogach. Tutaj agent w panelu jest klientem MCP: łączy się z tym samym obiektem serwera przez transport in-memory z SDK (mcp.shared.memory). Skutek: co działa w panelu, działa z terminala, i odwrotnie. Ten sam db_query odpowiada na pytanie zadane w przeglądarce i na wywołanie z Claude Code.

stdiotask mcp → python -m agent.server. Protokół idzie standardowym wyjściem, więc żadne narzędzie nie ma prawa nic wypisać printem; log serwera podniesiony do WARNING.
HTTPTrasa /mcp w aplikacji ekranu korekty. Menedżer sesji powstaje w cyklu życia aplikacji.
in-memorycreate_connected_server_and_client_session(server) — bez gniazd, bez serializacji po sieci, ten sam kod narzędzi.

dwie pułapki, które to kosztowało

  • Gotowa aplikacja Starlette z SDK poszła do kosza. Zamontowana przez app.mount("/mcp", …) odpowiadała przekierowaniem 307 na /mcp/, za którym klient MCP nie idzie. Zamiast niej stoi trasa z gołym ASGI (McpEndpoint), a menedżer sesji i ochrona przed DNS rebinding zostają te same.
  • StreamableHTTPSessionManager.run() wolno wywołać raz na instancję. Aplikacja ekranu startuje w jednym procesie wiele razy (każdy moduł testów stawia własnego TestClient), więc menedżer powstaje w cyklu życia przez fabrykę agent.server.session_manager(), a nie jako singleton przy imporcie. Bez tego 73 testy padały na „can only be called once per instance".

zależności i wersje

Wszystkie MIT, sprawdzone 8.09.2026: mcp 1.30.0 (przypięte do <2, bo w 2.x FastMCP zmienił nazwę na MCPServer, a langchain-mcp-adapters wymaga 1.x), langchain 1.3.17, langgraph 1.2.11, langchain-mcp-adapters 0.3.2. Jedno SDK obsługuje i serwer, i klienta agenta.

Anatomia narzędzia od strony modelu

docstring jest interfejsem, adnotacje są kontraktem

Narzędzie definiuje się dekoratorem. Nazwa po angielsku, bo trafia do protokołu; opis po polsku, bo czyta go model i człowiek w liście narzędzi:

@mcp.tool(annotations=READ_ONLY)
def db_query(sql: str, limit: int = limits.MAX_ROWS) -> dict:
    """Dowolne zapytanie SQL tylko do odczytu (SELECT, WITH, EXPLAIN) na bazie korpusu.

    Transakcja READ ONLY, limit czasu 15 s, najwyżej `limit` wierszy (domyślnie 200)
    — wynik ucięty ma `truncated: true`. Korpus to widok `corpus_task`; tabela `task`
    zawiera też rekordy nierozstrzygnięte. Schemat: `db_schema`.
    """

Do klienta jedzie z tego pełna definicja. Tak wygląda ui_navigate tak, jak widzi go model:

{
  "name": "ui_navigate",
  "annotations": { "readOnlyHint": true, "destructiveHint": false, "openWorldHint": false },
  "inputSchema": {
    "type": "object",
    "properties": { "target": { "type": "object", "additionalProperties": true } },
    "required": ["target"]
  }
}

Adnotacje i metadane — po co model ma o nich wiedzieć

mcp.types.ToolAnnotations · meta
  • readOnlyHint: true — narzędzie niczego nie zmienia. Dostaje je 26 z 54 narzędzi; klient może je wołać bez pytania.
  • destructiveHint: true — dokładnie cztery: db_execute, ingest_db_reset, job_cancel, task_decide. Ostrzeżenie widoczne w każdym kliencie MCP, nie tylko w naszym panelu.
  • openWorldHint: true — narzędzia ingest_*, bo uruchamiają proces, który sięga poza bazę (mirror CKE, API modelu, Docker).
  • meta: {"confirm": true} — nasze pole, nie z protokołu: znaczy „to narzędzie chodzi przez bramkę zgody". Nosi je 13 narzędzi. Panel po nim rozpoznaje, że wynik {"confirm": …} nie jest błędem, tylko prośbą. Narzędzia ingest_* noszą w meta także nazwę zadania z Taskfile i grupę z menu.
Poprawka z 11.09.2026. Adnotacja readOnlyHint była do 11.09 obietnicą opartą wyłącznie na transakcji READ ONLY — a ta zatrzymuje zapis do bazy, nie zatrzymuje COPY … TO PROGRAM ani pg_read_file(). Przegląd kodu pokazał, że przez db_query da się uruchomić polecenie w kontenerze bazy, bo rola klucz jest superuserem. Dziś odczyt agenta chodzi na osobnej roli klucz_agent (migracja 0011): tylko SELECT, bez SUPERUSER, z limitem czasu ustawionym na roli — więc odmawia sama, także konstrukcjom, których dziś nie znamy. Osobne połączenie, a nie SET LOCAL ROLE, bo z połączenia superusera RESET ROLE wróciłby do pełnych uprawnień.
Wszystkie narzędzia zwracają słownik, nigdy goły tekst. Kształt jest przewidywalny: dane, url tam, gdzie istnieje odpowiednik w ekranie, truncated przy cięciu, hint z podpowiedzią, co zrobić dalej. Jedyny wyjątek to task_page_image, które oddaje obraz strony klucza jako treść obrazkową plus słownik z numerem strony.

Bramka zgody człowieka

protokół dwóch wywołań · jedna bramka na wszystkie wejścia

Najważniejsza decyzja projektowa całego agenta: zgoda nie jest okienkiem w panelu, tylko warunkiem wykonania wpisanym w narzędzie. Panel jest tylko miejscem, w którym człowiek klika.

  1. Model woła narzędzie bez confirmation

    Narzędzie liczy podgląd (dla db_execute — próba w transakcji, która zostaje wycofana; dla task_decide — stan i powody; dla przebiegu — linia polecenia), zakłada wiersz w agent_confirmation i zwraca {"confirm": {"id", "title", "preview", "cost_usd", "how"}}. Nic się nie zmieniło.

    zapis: żadenwynik: prośba, nie błąd
  2. Człowiek decyduje w panelu

    Karta zgody pokazuje tytuł, podgląd w <pre> i dwa przyciski. POST /api/agent/confirmations/{id} zapisuje decision i decided_at. Do decyzji pole pisania zostaje wolne — można najpierw dopytać agenta, co właściwie chce zrobić.

    tabela: agent_confirmationwartownik: sec-fetch-site
  3. Narzędzie woła się drugi raz, z confirmation=<id>

    confirm.consume sprawdza pod FOR UPDATE cztery rzeczy: czy zgoda dotyczy tego narzędzia, czy argumenty są dokładnie te same (porównanie jsonb po kanonicznej postaci), czy nie została już zużyta i czy decyzja to accept. Każdy inny stan to błąd z powodem po polsku. Dopiero potem leci zapis.

    jednorazowość: used_atodmowa: „człowiek odrzucił — nie ponawiaj"

Czego to nie przepuszcza

agent/confirm.py · schema/migrations/0010_agent.sql
  • Podmiany argumentów. Zgoda na UPDATE jednego wiersza nie przepuści innego zapytania — argumenty są przedmiotem zgody, nie sama nazwa narzędzia.
  • Drugiego użycia. Ta sama zgoda wykonuje się raz; kolejne wywołanie mówi „zostało już wykorzystane".
  • Wejścia od tyłu. Klient z terminala nie ma panelu, ale też nie ma obejścia: prośba ląduje w tej samej tabeli i czeka na kliknięcie w ekranie korekty. Nie ma flagi „wykonaj bez pytania".
  • Więzu w bazie. CHECK (used_at IS NULL OR decision IS NOT DISTINCT FROM 'accept'). Pierwsza wersja miała zwykłe =, co przy decision IS NULL daje NULL — a NULL w CHECK znaczy „przechodzi". Test zobaczył to na czerwono, zanim ktokolwiek zdążył na tym polegać.

Pętla agenta i strumień zdarzeń

przerwanie grafu zamiast drugiego czatu

Pętla to create_agent z LangChaina 1.x (agent/runtime.py): model z llm.chat_model, narzędzia z load_mcp_tools na sesji in-memory, checkpointer w pamięci procesu. Wątek grafu to identyfikator sesji, więc rozmowa ma ciągłość między turami.

Sztuczka, na której stoi zgoda w rozmowie: interceptor wywołań MCP, nie gotowe middleware. HumanInTheLoopMiddleware z LangChaina pytałoby o zgodę na podstawie samego wywołania — a podgląd („to zmieni 1 wiersz", „to kosztuje $3") potrafi policzyć tylko narzędzie, po zajrzeniu do bazy. Więc kolejność jest odwrotna: narzędzie wykonuje się na próbę, zwraca prośbę, a interceptor zamienia ją na interrupt() grafu.

class ConfirmInterceptor:
    async def __call__(self, request, handler):
        call_id = getattr(request.runtime, "tool_call_id", None)
        asked = PENDING_CONFIRMS.get(call_id)          # pamięć po id wywołania
        if asked is None:
            result = await handler(request)            # pierwsze przejście
            asked = parse_json(text_of(result))
            if not asked or "confirm" not in asked:
                return result                          # zwykłe narzędzie — koniec
            PENDING_CONFIRMS[call_id] = asked
        decision = interrupt({...})                    # graf staje; panel dostaje `confirm`
        if decision.get("decision") != "accept":
            return ToolMessage(..., status="error")    # odmowa wraca do modelu
        return await handler(request.override(         # wykonanie za zgodą
            args={**request.args, "confirmation": asked["confirm"]["id"]}))
Dlaczego pamięć po tool_call_id: graf po wznowieniu wykonuje węzeł od początku, więc bez niej narzędzie zostałoby zawołane na próbę drugi raz i założyłoby drugą prośbę o zgodę. Test sprawdza wprost, że po pełnym cyklu w agent_confirmation jest dokładnie jeden wiersz.

Zdarzenia, które widzi panel

agent/api.py · text/event-stream

Kawałek odpowiedzi. Panel domyka niedokończony markdown w locie (remend), więc niedomknięte ** jest pogrubieniem od pierwszej klatki.

Nazwa i argumenty. W rozmowie staje się chipem z rozwijanym wynikiem.

confirm
Prośba o zgodę z podglądem — karta z przyciskami.
usage
Tokeny wejścia i wyjścia oraz koszt tury policzony cennikiem llm.PRICING.
done
finished albo waiting — to drugie znaczy „graf stoi na przerwaniu".
error
Powód po polsku. Wyjątki z grupy zadań anyio są rozpakowywane, żeby komunikat nie zginął w ExceptionGroup.

co zostaje w bazie po turze

Wiadomość korektora, każda wiadomość modelu z tokenami i listą wywołań, wynik każdego wywołania w agent_tool_call (z identyfikatorem zgody, jeśli była). Po restarcie serwera panel odtwarza rozmowę z bazy. Stan grafu żyje tylko w procesie, więc przerwanie w toku po restarcie przepada — panel mówi to wprost („ta rozmowa na nic nie czeka"), zamiast wznawiać coś, czego nie ma.

Wybór modelu jest cechą sesji

agent/runtime.py · AGENT_MODELS

Trzy pozycje do wyboru w nagłówku panelu: openai:gpt-5.6-luna, -terra, -sol. Wybór zapisuje się w agent_session.model, a zmiana zakłada nową rozmowę — historia z jednego modelu nie miesza się z drugim, a koszt liczy się per model. Domyślny bierze się z AGENT_MODEL w .env. Model spoza listy odrzuca POST /api/agent/sessions z 400, także gdy jest w cenniku.

Pułapka, którą złapał pierwszy przebieg z żywym modelem: gpt-5.6 odrzuca narzędzia funkcyjne na /v1/chat/completions — „Function tools with reasoning_effort are not supported… use /v1/responses". Stąd use_responses_api=True dla dostawcy openai. Przebiegi verify i prefill tego nie widzą, bo używają structured output bez narzędzi.

System prompt, co do znaku

3974 znaki · trzy części · migawka liczona raz na sesję

Prompt składa się z trzech części zszywanych w prompts.system_prompt(): stałego opisu projektu i zasad, wygenerowanego spisu widoków ekranu, oraz migawki stanu bazy. Migawka powstaje raz na sesję — prompt ma być stały, żeby dostawca mógł go cache'ować, a agent znał liczby bez wydawania tury na pytanie o nie.

Pierwsza część, dosłownie:

Jesteś agentem projektu Klucz (faza alfa) — pomocnikiem korektora
w ekranie korekty i inspektorze danych. Odpowiadasz po polsku, zwięźle, w markdown.

Projekt: korpus zasad oceniania (kluczy) egzaminu ósmoklasisty z matematyki (CKE),
sparsowanych z PDF-ów do PostgreSQL, żeby silnik oceniania (C#) mógł oceniać
odpowiedzi uczniów według kryteriów. Warstwy: `ingest/` (Python: mirror PDF, parser,
migracje, ekran korekty, przebiegi LLM), `backend/` (C#: czyta gotową strukturę,
NIGDY nie parsuje PDF-a), `web/` (React). Kontraktem jest schemat bazy.

Słownik: task = zadanie, task_version = wersja (bliźniak X/Y), model_answer =
odpowiedź wzorcowa (zadania zamknięte), criterion = próg punktowy, criterion_condition
= warunek progu (LUB), condition_expression = zapis równoważny, asset = wycinek
graficzny, rule = „Uwagi ogólne" arkusza, document = PDF, exam_form = forma arkusza,
requirement = wymaganie podstawy programowej, marking_scheme = klucz, paper = zeszyt.

Bramka: parser produkuje kandydatów (`review_status = 'pending'`); korpusem jest
WIDOK `corpus_task` (`approved` — parser trafił sam, `corrected` — poprawione).
Kto rozstrzygnął, niesie `task.reviewed_by` (human / model / agent). Plan A2-auto:
wariant 100 rozstrzygnął model (`task verify`), człowiek sprawdza próbkę.

Zasady, których pilnujesz:
- Więzy bazy są ostre celowo (np. UNIQUE (task_id, points)). Rekordu odrzuconego
  przez więz nie wymuszasz — poprawiasz dane albo mówisz, że to robota dla człowieka.
- Zapis do korpusu wyłącznie narzędziami `task_*` / `asset_*`; `db_execute` tylko
  do rzeczy spoza korpusu, zawsze za zgodą człowieka.
- Narzędzia z potwierdzeniem zatrzymują rozmowę do decyzji człowieka w panelu.
  Nie dopytuj „czy na pewno" — panel to zrobi; po prostu wywołaj narzędzie.
- Przed płatnym przebiegiem z `--apply` obowiązuje dry-run na jednym roczniku.
- Zanim wyjaśnisz, jak coś działa, sprawdź w `docs_search` / `docs_read` /
  `code_search` / `code_read`. Nie zgaduj i nie wymyślaj liczb — weź je z narzędzi.
- Duże wyniki są przycinane (`truncated: true`) — wtedy zawęź zapytanie.
- Liczby zbiorcze licz w `db_query` (GROUP BY), nie przez wyliczanie wierszy.
  Rocznik i wariant siedzą na dokumencie klucza: `JOIN document d ON
  d.id = t.marking_scheme_id`, potem `d.year`, `d.variants` (lista po przecinku).
- Przebiegi ingestu (`ingest_*`) biegną w tle: po uruchomieniu sprawdzaj `job_status`
  i `job_log`, a po końcu czytaj raport z `report_read`, zamiast czekać w rozmowie.

Korektor patrzy na ekran: każda wiadomość niesie kontekst `[ekran: ...]` — widok,
zadanie, stronę, tabelę. Gdy prosi „pokaż", „zaprowadź", „otwórz" — użyj
`ui_navigate` (przejście po odpowiedzi) albo `ui_focus` (pole na otwartym formularzu).
Adresy składa narzędzie; nie wypisuj ich z pamięci.

Nawigacja ma ZOSTAWIĆ korektora w narzędziu. Prośbę „przejdź na stronę N" spełnia
widok, nie plik: `task` z `page` (strona klucza obok formularza zadania) albo
`inspect_record` z `pdf_page` (podgląd w wierszu; `table: "document"` dla samego
pliku). Celów `document_pdf` i `document_page` w `ui_navigate` nie używaj — to
surowe pliki; do otwarcia w nowej karcie jest `ui_open_pdf`.

Druga część powstaje z urls.VIEWS, więc nowy widok w budowniczym adresów pojawia się w promptcie sam:

Widoki ekranu (cele `ui_navigate`):
- `overview` — przegląd korekty: liczby, lista zadań w zakresie (`scope`, `status`)
- `next` — pierwsze nierozstrzygnięte zadanie w zakresie (`scope`)
- `task` — formularz korekty zadania (`id`, opcjonalnie `page` klucza, `scope`)
- `inspect` — spis tabel inspektora ze zdrowiem danych
- `inspect_list` — lista wierszy tabeli (`table`, `filters`, `sort`, `direction`, `page`, `all_columns`)
- `inspect_record` — wiersz tabeli z pochodzeniem (`table`, `id`, opcjonalnie `pdf_page`)
- `health` — lista wierszy jednej kontroli zdrowia (`key`)
- `document_pdf` — cały PDF z mirrora (`document_id`, opcjonalnie `page`)
- `document_page` — strona PDF jako PNG (`document_id`, `page`)

Trzecia część to migawka. Ta jest z 8.09.2026, prosto z bazy deweloperskiej:

Migawka jest skrótem, nie źródłem prawdy — mówi o sobie sama, że świeże liczby daje project_status. Dzięki temu agent nie zaczyna każdej rozmowy od dwóch wywołań na rozpoznanie sytuacji, a jednocześnie nie powtarza liczby, która zdążyła się zmienić.

Nawigacja i kontekst ekranu

adresy składa Python · przejście po zakończeniu odpowiedzi

Ekran korekty ma routing po stronie serwera, więc „zaprowadź mnie do zadania 42" to zwykłe przejście na adres. Adresów nie skleja model — składa je jedno miejsce w Pythonie (agent/urls.py), a cel przychodzi strukturą:

ui_navigate({"view": "inspect_list", "table": "task",
             "filters": {"kind": "open_short", "review_status": "pending"}})
        → /inspect/task?kind=open_short&review_status=pending

ui_navigate({"view": "task", "id": 42, "page": 7, "scope": {"year": 2025}})
        → /task/42?page=7&year=2025

Powód jest prosty: model pomyliłby _sort z sort albo składnię filtra, a taki adres wygląda jak działający i pokazuje pełną tabelę zamiast wyniku. Osobny test porównuje każdy adres z budowniczego z trasami w correction/app.py, więc adres bez trasy nie przejdzie przez bramkę CI.

Nawigacja ma zostawić korektora w narzędziu

tools/navigation.py · FILE_VIEWS

Pierwsza wersja miała dziurę widoczną dopiero w użyciu. Na prośbę „przejdź na stronę 16" agent wołał cel document_page — technicznie poprawnie, bo taka trasa istnieje. Tylko że ta trasa oddaje surowy PNG: przeglądarka wychodziła z aplikacji do gołego obrazka, bez panelu, bez przewijania stron, bez czegokolwiek dookoła.

Teraz ui_navigate zamienia taki cel na najbliższy widok w aplikacji — wiersz dokumentu w inspektorze, który ma podgląd strony z przewijaniem:

ui_navigate({"view": "document_page", "document_id": 54, "page": 16})
        → /inspect/document/54?_pdfpage=16
        + note: "Cel wskazywał surowy plik, który wyprowadza korektora z ekranu…"

Właściwe cele dla prośby o stronę zostają dwa: task z page (strona klucza obok formularza zadania) i inspect_record z pdf_page (podgląd w wierszu). Plik w nowej karcie ma osobne narzędzie, ui_open_pdf — tam wyjście z aplikacji jest tym, o co się prosi. ui_views wymienia cele, które nie są do nawigacji, a ta sama reguła stoi w promptcie.

Skąd agent wie, na co patrzy korektor

ui/src/agent/screenContext.ts

Panel i widok to osobne korzenie Reacta i nie dzielą stanu, więc kontekst czyta się z tego, co widzą oba: adresu i atrybutu data-view na skorupie strony. Z każdą wiadomością jedzie linia przed treścią pytania:

[ekran: view=task, path=/task/42, query=?page=7, task_id=42, page=7]

Ile progów ma to zadanie?

Dzięki temu „to zadanie" znaczy zadanie 42, a nie „które zadanie?". Kontekst zapisuje się też w agent_session.screen — wiadomo, z którego ekranu rozmowa wystartowała.

dlaczego przejście dopiero po zakończeniu odpowiedzi

Przeładowanie strony w połowie strumienia urwałoby odpowiedź. Panel pokazuje więc chip z adresem od razu, a window.location.assign wykonuje po zdarzeniu done. Rozmowa jest w bazie, więc po wczytaniu nowej strony panel odtwarza ją z GET /api/agent/sessions/{id} i wygląda to jak jedna ciągła sesja. To także powód, dla którego rozmowa musi żyć na serwerze, a nie w localStorage.

Przebiegi ingestu w tle

proces, log w pliku, rejestr w bazie

Przebieg ingestu trwa minuty albo godziny, więc nie może blokować rozmowy. ingest_* uruchamia task <nazwa> -- <flagi> jako proces potomny i wraca natychmiast z numerem przebiegu. Rejestr jest w agent_job, wyjście w data/reports/jobs/<data>-<zadanie>.log.

Podział jest celowy: rejestr w bazie, log na dysku. Ekran korekty chodzi z --reload, więc proces serwera restartuje się przy każdej zmianie pliku; przebieg ma to przeżyć i nie zniknąć z listy.

Cztery szczegóły, które sprawiają, że to działa na Windows

agent/jobs.py
  • Osobna grupa procesów (CREATE_NEW_PROCESS_GROUP, na POSIX start_new_session). Anulowanie trafia w przebieg, nie w serwer, a na Windows tylko grupa przyjmuje CTRL_BREAK.
  • PYTHONIOENCODING=utf-8 do procesu potomnego. Bez tego proces przechwycony przez rodzica pisze w kodowaniu konsoli (cp1250) i polskie znaki w logu rozsypują dekodowanie — pułapka spisana w CLAUDE.md.
  • Kod wyjścia ze znakiem. Windows oddaje NTSTATUS bez znaku (CTRL_BREAK to 0xC000013A), a kolumna jest 32-bitowa ze znakiem. Pierwsza wersja kończyła się „integer out of range" przy anulowaniu.
  • Stan unknown, nie finished. Przebieg uruchomiony przed restartem serwera nie ma już uchwytu procesu. Zamiast zgadywać, że skończył, narzędzie mówi wprost: stan znany tylko z logu, pid taki i taki, zatrzymaj ręcznie jeśli trzeba.
Płatne przebiegi (verify, prefill, describe, frame, golden set) i kasujące (db:reset) idą przez bramkę zgody, a podgląd niesie dokładną linię polecenia. Gdy w argumentach jest --apply, podgląd dokłada przypomnienie reguły z 4.09: najpierw dry-run na jednym roczniku. Ta reguła kosztowała $1,38 i wykryła błąd systematyczny parsera na 1346 zadaniach.

Pierwsza tura z żywym modelem, rachunek do obejrzenia

smoke 8.09.2026 · openai:gpt-5.6-luna

Pytanie: „ile zadań czeka na rozstrzygnięcie w roczniku 2025 i które z nich są otwarte?". Przebieg: task_find → db_query (błąd: „column year does not exist") → db_schema na task i document → poprawiony db_query z JOIN → odpowiedź. Sześć wywołań, sto kawałków strumienia, poprawny wynik, $0,039.

Dwie rzeczy z tego wynikły. Pierwsza: agent naprawił własny błąd SQL bez pomocy, czyli komunikaty narzędzi są wystarczające. Druga: 190 tysięcy tokenów wejścia, bo task_find oddał 201 pełnych wierszy — stąd sufit 100 zwięzłych wierszy i zdanie w promptcie o GROUP BY. Ten sam mechanizm, który przy człowieku odróżnia pytanie o liczbę od prośby o listę.

luna$0,20 / $1,20 za milion tokenów — do odczytu i nawigacji.
terra$2 / $12 — domyślny; jakość użycia narzędzi ważniejsza niż cena.
sol$4 / $20 do 21.11.2026, potem $5 / $30. Cennik do poprawienia po tej dacie, inaczej raport zaniży koszt.

Koszt nie jest kwestią wiary: task correction:report i task corpus:report mają sekcję Agent w ekranie korekty z sesjami, turami, tokenami i dolarami rozbitymi na modele, liczbą wywołań narzędzi i liczbą zgód (przyjętych, odrzuconych, czekających).

Bez klucza dostawcy w .env panel wraca do makiety i mówi dlaczego — GET /api/agent/config zwraca wtedy mode: "mock" z powodem. To samo daje AGENT_MODEL=mock, gdy chce się pokazać ekran bez wydawania tokenów.
