Czym jest ingest i gdzie się kończy

granica warstw

Ingest to warstwa Pythona, która pracuje offline. Nie obsługuje żadnego ruchu użytkownika. Uruchamia się ją ręcznie z terminala, a jej jedynym wynikiem są dane: wiersze w PostgreSQL i pliki PNG na dysku. Backend w C# czyta gotową strukturę i nigdy nie otwiera PDF-a.

Kontraktem między warstwami nie jest API, tylko schemat bazy (pliki SQL w ingest/schema/migrations/) plus pliki JSON golden setu. Dlatego schemat stoi jako czysty SQL, a nie model wyprowadzony z kodu.

Najważniejsza zasada, którą trzeba mieć w głowie czytając resztę: parser produkuje kandydatów, nie korpus. Rekord z parsera trafia do tabeli task ze statusem pending. Do korpusu wchodzi dopiero po rozstrzygnięciu w ekranie korekty (człowiek) albo przez drugiego czytelnika (model, plan A2-auto). Konsumenci czytają widok corpus_task, który zawiera tylko rekordy approved i corrected.

Cały proces w jednym spojrzeniu

kolejność ma znaczenie, każdy krok czyta wynik poprzedniego

Każde polecenie to task <nazwa> z Taskfile.yml, które pod spodem woła uv run python -m <moduł> z katalogu ingest/. Argumenty przekazuje się po --, np. task ingest -- --year 2025 --variant 100. Kto nie chce pamiętać flag, uruchamia task menu (sekcja 03a): to samo, tylko z listy i z pytaniami.

  1. Zwózka mirroratask mirror

    Pobiera strony rocznikowe z cke.gov.pl, wyciąga z nich linki do PDF-ów, buduje spis i ściąga pliki. Jednorazowo; kolejne uruchomienia dosypują brakujące.

    moduł mirror/cke_mirror.pywyjście data/index/urls.tsv, data/raw/**/*.pdf
  2. Baza i migracjetask up · task migrate

    Postgres w Dockerze plus runner migracji, który stosuje brakujące pliki SQL w kolejności numerów i pilnuje sum SHA-256 tych już zastosowanych.

    moduł schema/migrate.pywyjście tabele korpusu, tabela schema_migrations
  3. Parser i ładowanietask ingest

    Dla każdego klucza oceniania: warstwa PDF odtwarza tekst z matematyką, parser tnie go na zadania, kryteria, odpowiedzi i wymagania, ładowarka zapisuje to w jednej transakcji per klucz. Z flagą --with-papers doczytuje zeszyty zadań: treść i ramki rysunków.

    moduły pdf/*, parsers/omap_e8/{parser,loader,run}.pywyjście task, criterion, asset … (status pending); data/reports/ingest-DATA.txt
  4. Wycinki PNGtask crops

    Tnie z zeszytu zadań fragmenty stron według ramek zapisanych w asset.bbox. Działa po ładowaniu, poza transakcją, bo dysk nie cofa się razem z bazą.

    moduł parsers/omap_e8/crops.py + pdf/crop.pywyjście data/blob/OMAP/<sesja>/<wariant>/<wersja>/zN-i.png
  5. MathJSONtask mathjson

    Zapisy równoważne z kryteriów („P = 1/2·15·2”) zamienia na LaTeX w Pythonie, a potem na MathJSON w Node przez Compute Engine. Odmowy dostają jawny status failed z powodem.

    moduły mathjson/{normalize.py,convert.mjs,fill.py}wyjście condition_expression.mathjson + mathjson_status
  6. Bramka: rozstrzygnięcie rekordutask correction · task verify

    Człowiek w ekranie korekty na localhoście albo model w task verify porównuje rekord ze stroną klucza i zatwierdza, poprawia lub odrzuca. Dopiero to zmienia review_status i wpuszcza rekord do widoku corpus_task.

    moduły correction/{app,db,verify}.pywyjście task.review_status, task.reviewed_by, dziennik correction_event
  7. Wzbogacenie modelemtask prefill · task describe · task frame

    Podpowiedzi kryteriów do ekranu (pomiar S6), opisy rysunków jako alt-text (S7) i ramki rysunków z siatki tam, gdzie automat geometryczny nie domknął. Ręczne, płatne, nigdy w CI.

    moduły correction/{llm,prefill,describe,frame}.pywyjście prefill_suggestion, asset.description (auto), asset.bbox
  8. Golden set i raportytask golden:generate · task golden:grade · task corpus:report

    Model A pisze odpowiedzi ucznia do zadań otwartych z korpusu, model B je ocenia wg klucza. Raport kompletności liczy definicję „zrobione” dla A2 dwa razy: po korpusie i po całym sparsowanym materiale.

    moduły golden/{generate,grade}.py, reports/corpus.pywyjście ingest/golden/<rok>/task-N.json, data/reports/corpus-A2-DATA.txt

Środowisko: co musi stać, żeby cokolwiek ruszyło

jedno wejście: task, konfiguracja: .env

Wszystkie polecenia idą przez go-task, który ma wbudowany interpreter POSIX sh, więc te same komendy działają na Windows, macOS i w CI. Python uruchamia uv (uv run python -m …), zależności są przypięte w ingest/uv.lock.

Konfiguracja stoi w .env w korzeniu phase-alfa/ (wzór w .env.example). Taskfile ładuje ten plik automatycznie (dotenv: ['.env']).

Uruchamianie modułami, nie ścieżkami. Korzeniem pakietu jest ingest/, więc uv run python -m parsers.omap_e8.run działa, a python parsers/omap_e8/run.py nie: przy uruchomieniu przez ścieżkę sys.path wskazuje katalog pliku i importy między pakietami (pdf.layout, schema.migrate) się sypią.

Menu: task menu zamiast flag z pamięci

questionary + rich; kategoria → akcja → pytania → podgląd komendy → uruchomienie

cli/app.py

ingest/cli/app.py · task menu → uv run python -m cli

Wszystkie polecenia z tabeli wyżej da się uruchomić bez pisania komendy: strzałkami wybierasz akcję, odpowiadasz na pytania o flagi, oglądasz gotową linię i potwierdzasz. Menu jest cienką warstwą nad Taskfile, nie drugą implementacją: składa task <nazwa> -- <flagi> i uruchamia je z korzenia repo, więc .env, katalog ingest/, komunikaty i kody wyjścia są dokładnie te same, co przy ręcznym wywołaniu.

Jak to działa

  1. Katalog akcji (CATALOG) to dane: grupy (baza, mirror, parser, korekta, LLM, MathJSON, raporty), a w nich Action(task, title, about, params, paid, destructive, foreground). Każdy Param to jedna flaga z rodzajem pytania: text, int, bool (flaga bez wartości), choice (lista, np. roczniki 2019–2026, warianty, modele z cennika llm.PRICING) albo words (kilka wartości, jak --compare stary.json nowy.json).
  2. Dwa poziomy list. Najpierw kategoria (nazwa, liczba akcji, zdanie opisu), potem akcje tej kategorii: tytuł, znacznik ([$] płatne, [!] kasuje, [⏵] stoi do Ctrl-C), nazwa zadania i opis w jednej linii. Po wyborze akcji karta z opisem i tabelą flag (pytanie, rodzaj, co znaczy), dopiero potem pytania.
  3. Pytania zadaje questionary; pusta odpowiedź, „(bez flagi)” albo „nie” znaczą „bez tej flagi”. Pola liczbowe przyjmują tylko cyfry. Ctrl-C w środku pytań wraca do kategorii, na liście kategorii wychodzi.
  4. build_args() (funkcja czysta, testowana) zamienia odpowiedzi na listę argumentów w kolejności z katalogu, a command_for() dokleja task i -- tylko wtedy, gdy są flagi.
  5. Podgląd w panelu rich: opis akcji, dokładna komenda, ostrzeżenia. Akcje płatne ([$]: verify, prefill, describe, frame, golden) wymagają wpisania PŁACĘ, kasujące ([!]: db:reset) wpisania KASUJ. Reszta: Enter.
  6. Uruchomienie przez subprocess.run z odziedziczonym terminalem, więc wyjście skryptu leci na żywo, a serwer korekty i konsola psql (foreground) stoją do Ctrl-C lub \q, po czym menu wraca. Kod wyjścia jest tłumaczony: 0 dobrze, 1 poniżej progu lub różnice, 2 nie ruszyło.
  7. Własne polecenie task… na końcu listy przyjmuje dowolne zadanie spoza katalogu (test:contract, dev).

Czego pilnuje test

tests/test_cli.py sprawdza, że każda nazwa zadania z katalogu istnieje w Taskfile.yml (regex po nazwach na początku linii), że każda flaga z katalogu występuje w --help odpowiedniego modułu (menu nie może wymyślać własnych flag), oraz zachowanie build_args: pomijanie pustych i fałszywych, flaga bool bez wartości, kolejność jak w katalogu. Warstwa interaktywna (questionary, rich) ładuje się leniwie, więc testy nie potrzebują terminala.

Jak działa, krok po kroku

  1. Spis. collect_inventory() pobiera każdą stronę rocznikową (np. cke.gov.pl/egzamin-osmoklasisty/arkusze/2025-2/), zapisuje surowy HTML w data/index/pages/<segment>-<rok>.html i wyciąga regexem wszystkie href kończące się na .pdf. Adresy są normalizowane (normalize_url: absolutny https, bezpieczna ścieżka, host bez www) i odsiewane z duplikatów.
  2. Metadane z nazwy pliku. parse_filename() rozkłada OMAP-100-2505-zasady.pdf na kod (OMAP), warianty (100), sesję (2505 → 2025-05) i typ dokumentu. Typ rozpoznaje w czterech miejscach po kolei: prefiks nazwy (rocznik 2019: Zasady_oceniania_…), sufiks (od ok. 2022: …-zasady, …-zeszyt-zadan), katalog w URL (2020–2021) albo wartość domyślna arkusz. Kolumna zrodlo_typu mówi, skąd wynik. Sesja jest szukana od prawej strony tokenów, bo w maturze po sesji stoi jeszcze wariant.
  3. Zapis spisu. write_inventory() tworzy data/index/urls.tsv (jeden wiersz na plik, 13 kolumn: segment, rocznik, podkatalog, plik, kod, warianty, sesja, typ, zrodlo_typu, wzorzec, url, sciezka_lokalna) i manifest.json z licznikami.
  4. Pobieranie. download_all() puszcza ThreadPoolExecutor z 8 wątkami. download_one() pomija plik, który już leży na dysku i ma rozmiar większy od zera. Pobrany bajt sprawdza pod kątem sygnatury %PDF, zapisuje do .part i podmienia atomowo (tmp.replace(dest)), więc w mirrorze nigdy nie ma pół pliku. Trzy próby z rosnącym odstępem; HTTP 404, 403 i 410 nie są ponawiane.
  5. Raport. build_report() porównuje spis ze stanem dysku, sprawdza sygnaturę każdego pliku i pisze data/reports/kompletnosc.md, kompletnosc.csv, braki.tsv oraz dopisuje do download-log.tsv. Kod wyjścia 1, gdy są braki lub pliki uszkodzone.
Flagi mirrora są jeszcze po polsku (--filtr, --rocznik, --tylko-spis, --cicho), inaczej niż w reszcie ingestu. Ten sam plik żyje w repozytorium cke-mirror, więc zmiana nazw musi pójść w obu miejscach naraz.

Typowe wywołania

task mirror -- --filtr matematyka        # tylko pliki ze ścieżką zawierającą „matematyka"
task mirror -- --dry-run                 # nic nie pobiera, raport ze spisu na dysku
task mirror -- --tylko-spis              # odśwież urls.tsv, nie ściągaj PDF-ów
task mirror -- --rocznik 2026 --jobs 4   # jeden rocznik, mniej strumieni

Schemat bazy i migracje

kontrakt między Pythonem a C#, więzy zostają ostre

Jak działa runner

  • Adres bazy bierze wyłącznie z konfiguracji (polaczenie(): DATABASE_URL albo pięć zmiennych DB_*). Brak zmiennej kończy się komunikatem, nie stack trace'em.
  • Tworzy tabelę schema_migrations (version, applied_at, sha256), jeśli jej nie ma.
  • Liczy SHA-256 każdego pliku po normalizacji BOM-u i CRLF (suma()). Migracja, która już weszła, a ma inną sumę, zatrzymuje runner z napisem ROZJAZD. Zastosowanej migracji się nie edytuje, dopisuje się nową.
  • Każdy brakujący plik wykonuje w jednej transakcji razem z wpisem do schema_migrations. Połączenie jest w autocommit=True, bo bez tego conn.transaction() zakładałby tylko savepoint i wszystkie migracje lądowałyby w jednej transakcji.
  • Pliki SQL nie mają BEGIN/COMMIT. Transakcję otwiera runner.

Jak zbudowany jest model

Dokument (document) to jeden PDF z mirrora: klucz oceniania (marking_scheme) albo zeszyt zadań (paper). Forma arkusza (exam_form) to to, co uczeń dostaje na stole: kod, wariant dostosowania (100, 200, 400, 700, 800, C00, K00, Q00), wersja bliźniacza (X/Y) i sesja. Tabela exam_form_document spina je N:M z rolą.

Zadanie (task) wisi na kluczu i niesie numer, pulę punktów, rodzaj, stronę w kluczu, status korekty. Kryteria (criterion → criterion_condition → condition_expression) i wymagania podstawy (task_requirement) wiszą na zadaniu, bo bliźniaki X i Y dzielą kryteria. Wersja zadania (task_version) wisi na formie i niesie to, co bliźniaki różni: treść z zeszytu, odpowiedź wzorcową (model_answer) i rysunek (asset).

Trzy poziomy kryteriów to trzy poziomy alternatywy: próg (ile punktów) jest osiągnięty, gdy spełniony jest dowolny warunek, a warunek, gdy uczeń zapisał dowolny z równoważnych zapisów. Więz UNIQUE (task_id, points) na criterion złapał w sondzie prawdziwy błąd parsera i dlatego nikt go nie luzuje.

Reguły przekrojowe (rule) to sekcja „Uwagi ogólne” klucza (błąd rachunkowy, sam wynik za 0 pkt) z zakresem zadań tasks_from–tasks_to. Uwagi spod pojedynczego zadania też lądują tutaj, z zakresem równym numerowi zadania i pozycją 1000+.

layout.py: jedno API, dwa silniki

ingest/pdf/layout.py

Otwiera PDF przez open_pdf(path, engine) i oddaje strony jako obiekty Page z czterema leniwie liczonymi warstwami:

  • chars: każdy glif jako Char(c, x0, x1, y0, y1, size); y0/y1 liczone od górnej krawędzi strony.
  • bars: kreski kandydujące na kreskę ułamkową. Linia albo prostokąt o grubości ≤ 1,6 pt i długości od 3 do 90 pt (_is_bar). Odsiewane są te, które leżą wewnątrz wykrytej tabeli, bo to krawędzie komórek. find_tables() kosztuje ok. dwa razy tyle co reszta, więc uruchamia się tylko gdy są kandydaci.
  • tables: tabele z pdfplumbera z rozwiniętymi komórkami (potrzebne do wymagań podstawy).
  • shapes: obrazy, krzywe, prostokąty, linie z ramkami (x0, top, x1, bottom); wejście wykrywania regionu graficznego.

zrzut_strony() zapisuje te warstwy do JSON, a StronaZeZrzutu odtwarza z nich stronę o tym samym interfejsie. Na tym stoją testy regresji bez ani jednego PDF-a w repozytorium (tests/fixtures/strony-omap-100-2505.json, arkusz-omap-100-x-2505.json).

reconstruct.py: matematyka z geometrii strony

ingest/pdf/reconstruct.py

Płaska ekstrakcja tekstu gubi ułamki i potęgi: licznik, kreska i mianownik to trzy osobne obiekty na różnych wysokościach. Ten moduł składa je z powrotem.

Ułamki

_pietra(chars, bar) szuka znaków nad i pod kreską w oknie 1,45 × rozmiar pisma (mediana rozmiaru w wierszu, nie pierwszy znak). Znak należy do kreski, gdy jego środek mieści się w jej zasięgu z zapasem 1,2 pt. _fits() odrzuca piętro, które jest słowem (≥ 3 litery), bo podkreślenie pod nagłówkiem „Uwagi” przechodziło wszystkie testy geometryczne i dawało ułamek Uwagi/1. render() obsługuje ułamki zagnieżdżone rekurencyjnie (kreska wewnątrz zasięgu innej kreski) i wypisuje licznik/mianownik.

Potęgi i indeksy

_mark_scripts() uznaje znak za indeks, gdy jest mniejszy niż 0,82 rozmiaru bazowego i przesunięty o więcej niż 0,18 wysokości fontu: w górę daje ^, w dół _. Ciąg k^-^1^0 jest scalany do k^(-10), a P_A_E_C_F do P_(AECF).

Normalizacja i wiersze

normalize() sprowadza kursywę matematyczną Unicode (U+1D400–U+1D7FF) do zwykłych liter przez NFKC i wszystkie warianty myślnika do minusa. page_text() grupuje znaki w wiersze co 3 pt, ale wcześniej kotwiczy piętra ułamków i indeksy do najbliższego wiersza tekstu bazowego, żeby ułamek stojący w zdaniu nie wylądował w osobnej linijce. Wiersz tnie na segmenty tam, gdzie odstęp przekracza 25 pt (rynna między kolumnami). Liczba mieszana dostaje spację przed ułamkiem: 1 2/3 km, nie 12/3 km, bo sklejona wersja wyglądała jak poprawny ułamek o innej wartości.

Przypisy

przypisy() znajduje blok u dołu strony złożony z wierszy mniejszych od tekstu bazowego, pod warunkiem że w bloku jest wiersz o rozmiarze przypisu (≤ baza − 1,5 pt). Parser odcina go od treści, ale czyta z niego numer Dziennika Ustaw, po którym poznaje obowiązującą podstawę programową.

Świadomie nie działa: pierwiastki. Zasięg daszka jest w geometrii niejednoznaczny, wystąpień jest mało, a brak domknięcia widać w ekranie. Test test_pierwiastek_ma_zasieg stoi jako xfail z powodem „ŚWIADOMIE: korekta ręczna”, a konwerter MathJSON odmawia takich zapisów wprost.

regions.py: gdzie na stronie jest rysunek

ingest/pdf/regions.py · G2.4.1

detect(page, top, bottom) dostaje pionowy pas zadania (od jego nagłówka do nagłówka następnego) i oddaje listę ramek. Diagram to zwykle kilkadziesiąt kresek, które mają zostać jednym zasobem.

  1. Kandydaci. Kształty, których co najmniej połowa wysokości leży w pasie. Trzy sita, każde zmierzone na arkuszu: kreska pod odpowiedź ucznia (≤ 1 pt grubości i ≤ 20 pt długości; jedna strona ma ich 4479), linijka strony (≥ 95% szerokości kolumny tekstu przy wysokości ≤ 20 pt), oraz limit 400 kandydatów, powyżej którego strona jest ozdobna i automat oddaje pole człowiekowi.
  2. Klastrowanie. cluster() scala ramki oddalone o mniej niż 8 pt (mniej niż odstęp między wierszami, ok. 12 pt) i powtarza przejścia do skutku, bo A styka się z B, B z C, a A z C już nie.
  3. Odsiew klastrów. Odpadają za małe (bok < 24 pt albo pole < 2500 pt²) i te rozpięte na ≥ 97% szerokości kolumny: to tabela „Prawda/Fałsz”, nie rysunek. Wykres z 2025 r. zajmuje 0,86 kolumny, tabela 0,99, więc próg rozdziela je z zapasem. Filtrowania po wykrytych tabelach nie ma celowo: pdfplumber widzi w wykresie słupkowym tabelę o dziewięciu wierszach.
  4. Margines. Każda ramka dostaje 6 pt zapasu i jest przycięta do strony.

Pusta lista znaczy „automat nie domyka”. Parser zapisuje wtedy ramkę całej strony [0, 0, szerokość, wysokość], a dociąga ją człowiek w ekranie albo model w task frame. Zmierzone na całym korpusie: 558 z 607 zasobów (92%) dostało ramkę z automatu.

crop.py: wycinek PNG

ingest/pdf/crop.py

crop(pdf_path, page, bbox, relative_target) renderuje fragment strony przez pypdfium2 w 200 DPI (skala 200/72) i zapisuje PNG pod BLOB_ROOT/relative_target. Jedna funkcja dla trzech źródeł ramki: automat, ręczne pola formularza, model. Różnią się wyłącznie tym, skąd bierze się bbox.

Dwie pułapki, które ten plik zamyka: bbox jest w punktach PDF od lewego górnego rogu (jak top/bottom w layout.py), a pdfium chce marginesów w kolejności lewy, dolny, prawy, górny, stąd przeliczenie (x0, height − bottom, width − x1, top). Numer strony jest liczony od 1, jak w stopce PDF-a. target_path() odmawia ścieżki wychodzącej poza korzeń blobów. Każdy błąd wychodzi jako CropError z powodem po polsku, do pokazania w ekranie.

parser.py

ingest/parsers/omap_e8/parser.py · 972 linie · awans z research/ bez zmian logiki

czytaj_klucz(path) zwraca obiekt Klucz z listą Zadanie. Wszystko po polsku, w języku dokumentu (zamkniete, zasady_oceniania), bo parser czyta polskie klucze. Tłumaczenie na angielski schemat robi dopiero ładowarka.

Przebieg dla jednego klucza

  1. Strona po stronie. Dla każdej strony: tekst z reconstruct.page_text(page, pomin_przypisy=True), pozycje nagłówków zadań (_heading_positions: wiersz zaczynający się od „Zadanie N. (0–k)”), stopka z przypisami, oraz tabele, w których w pierwszych pięciu wierszach stoi słowo „Wymagani”. Tekst wszystkich stron skleja się w jeden string; parser pamięta granice stron, żeby potem policzyć numer strony zadania (strona_offsetu, od 1).
  2. Dialekt. wykryj_dialekt() mierzy tekst, nie zgaduje z nazwy. „Egzamin maturalny” w pierwszych 4000 znakach → matura lub matura-2015 (gdy jest wzorzec „Zdający otrzymuje … N pkt”). Pagina „Egzamin ósmoklasisty z … – termin … r.” → e8-2020. Reszta → e8-2019. Dialekt (Dialekt, klasa zamrożona) niesie komplet regexów: postać progu, separator warunków (LUB/lub/ALBO), separator zapisów (albo/lub w osobnej linii lub odsunięte trzema spacjami), czytniki odpowiedzi, nagłówek rozwiązań, „I sposób”, „Uwagi”, „Uwagi ogólne”, koniec części zadaniowej i paginę do wycięcia.
  3. Reżimy, termin, formy. _rezimy() rozpoznaje podstawę programową z podpisu tabeli i z przypisu (poz. 996 lub 1019 → pp2024, poz. 356 → pp2017, poz. 977 → pp2012, „Wymagania egzaminacyjne 2021” → wym2021). _termin() czyta „Termin egzaminu: 14 maja 2025” na datę. _formy() czyta nagłówek „Formy arkusza: OMAP-100-2505 (wersje X i Y), OMAP-200-2505 …” i to jest sedno relacji N:M.
  4. Cięcie na zadania. _tnij_zadania() dzieli tekst po nagłówkach RE_ZADANIE; ostatnie zadanie kończy się na nagłówku „Ogólne zasady oceniania” lub podobnym (koniec_zadan), inaczej sekcja reguł doklejałaby się do ostatniego zadania.
  5. Parowanie tabel wymagań. _sparuj_tabele() przypisuje tabelę do najbliższego nagłówka nad nią (z tolerancją 6 pt, bo ramka tabeli bywa tuż nad nagłówkiem). Parowanie kolejnością przesuwałoby resztę, gdy jedno zadanie nie ma tabeli.
  6. Jedno zadanie. _parsuj_zadanie() najpierw wycina paginę, potem czyta odpowiedzi (_odpowiedzi), rozwiązania przykładowe (_rozwiazania), a tekst kryteriów bierze od „Zasady oceniania” do wcześniejszego z dwóch nagłówków: rozwiązań albo bloku odpowiedzi „Rozwiązanie – wersja X/Y”. Ta druga granica to poprawka z 4.09.2026: bez niej blok odpowiedzi wchodził do warunku za 0 pkt w każdym zadaniu zamkniętym od 2020 r. Sekcja „Uwagi” pod zadaniem jest odcinana i staje się regułą tego zadania. Typ: zamkniete, gdy są odpowiedzi bez rozwiązań; otwarte_krotkie do 2 pkt; inaczej otwarte_rozszerzone.
  7. Kryteria. _kryteria() znajduje progi (nagłówek „2 punkty” lub linia „1 pkt –”), sortuje po pozycji, dedupuje po punktach (pierwszy wygrywa), tnie blok każdego progu separatorem alternatywy na warunki, a warunek separatorem zapisu na zapisy równoważne. Granicą pierwszego zapisu jest „np.”, które w kluczach CKE wprowadza zapis, nie zdanie.
  8. Odpowiedzi. Trzy czytniki: wersje (nagłówek „Rozwiązanie – wersja X / wersja Y”, dwie kolumny rozdzielane wierszami lub podpunktami 1.1/1.2), ab (matura: „Wersja A / Wersja B”), solo (sama linia „Rozwiązanie”). Pozycja pierwszego trafienia jest granicą tekstu kryteriów.
  9. Wymagania. parsuj_wymagania() znajduje pary kolumn „Wymagania ogólne / szczegółowe” (rocznik 2019 ma dwie pary, bo mapuje na dwie podstawy), reżim bierze z podpisu nad kolumnami albo z kolejności, wykrywa etap („KLASY IV–VI”, „VII–VIII”) i ścieżki: dział rzymski + punkt arabski (XI.3) w E8 albo jawne (I.1), XIII.R1)) w maturze.
  10. Reguły. _reguly() czyta sekcję „Uwagi ogólne”, klasyfikuje każdą (rodzaj_reguly: rachunkowa, sam_wynik, sprzeczne_rozwiazania, dostosowanie, kalkulator, inna) i wyciąga zakres „w zadaniach 16–21”.
  11. Ostrzeżenia. Do Klucz.ostrzezenia trafiają m.in.: brak formy w nagłówku, zadania bez wymagań, otwarte bez kryteriów, zamknięte bez odpowiedzi. Osobno: „zadania zamknięte bez kryteriów mimo klucza, który je ma”. closed_without_criteria() mierzy, czy w tym kluczu jakiekolwiek zadanie zamknięte ma kryteria. Jeśli żadne, to norma dokumentu (rocznik 2019), a nie dziura.

Zeszyt zadań: czytaj_arkusz()

Dla każdej strony zeszytu: tekst, nagłówki zadań i ich pasy (_task_bands). Treść zadania to tekst od nagłówka do następnego nagłówka, obcięty do 1500 znaków. Jeśli treść wspomina wykres, diagram, rysunek, siatkę albo oś liczbową (graphic_kind), parser woła regions.detect w pasie zadania. Więcej niż 3 ramki na stronie znaczy rozsypany klaster i całą listę oddaje się człowiekowi (frames_for_assets). Brak ramki daje zasób z ramką całej strony. Zasoby liczą się raz na stronę, bo numer zadania trafia się na dwóch stronach.

Kolejność zapisu w jednej transakcji per klucz

  1. _wyczysc_klucz(): szuka dokumentu po URL. Jeśli klucz ma zadania ze statusem innym niż pending, rzuca ReviewedKeyError, chyba że overwrite_reviewed=True. Ta bramka stoi tuż przed DELETE, więc obowiązuje każdą drogę: runner, testy, ekran. Dopiero potem kasuje zadania, reguły i powiązania form tego dokumentu.
  2. Reżimy wymagań (ON CONFLICT (code) DO NOTHING; inna nazwa dla tego samego kodu ląduje w kolizje_rezimow).
  3. Dokument klucza: INSERT … ON CONFLICT (url) DO UPDATE, przy czym ingest_status wraca na new, bo zadania właśnie zniknęły i wchodzą od nowa.
  4. Formy arkusza z nagłówka, każda wersja osobno; forma własna pliku to ta z jego nazwy (RE_WLASNA_FORMA), bo zeszyt istnieje tylko dla niej. Gdy nagłówka „Formy arkusza” nie ma (2019, 2020), forma powstaje z nazwy pliku.
  5. Zeszyty zadań jako dokumenty paper z liczbą stron (ekran pokazuje „strona N z M”).
  6. Zadania: task (ze stroną w kluczu), task_requirement (wymagania przez ON CONFLICT (regime_id, kind, stage, path) DO NOTHING; inna treść pod tą samą ścieżką trafia do kolizje_wymagan, do bazy wchodzi pierwsza), task_version per wersja własna z treścią z zeszytu, model_answer (gdy forma nie ma litery wersji, a klucz podaje dwie kolumny, bierze pierwszą), asset ze ścieżką kod/sesja/wariant/wersja/zN-i.png, kryteria trzech poziomów, rozwiązania przykładowe, uwagi jako reguły.
  7. Reguły przekrojowe klucza.

Po wycofanej transakcji zapomnij_slowniki() czyści pamięć identyfikatorów, bo te z cofniętej transakcji już nie istnieją.

Kasowanie to checkbox delete.<prefiks>.<id> (tylko answer, criterion, condition, expression; wersji nie, bo kaskadą zabrałaby odpowiedzi i zasoby). Wymagania: add_requirement=<id> i delete.requirement.<id>. Zasoby: asset.<id>.x0|top|x1|bottom|page, asset.<id>.description, asset.<id>.approve_description.

Każdy UPDATE i DELETE ma doklejony warunek przynależności do zadania (OWNERSHIP), więc podmieniony identyfikator w formularzu nie sięga do cudzego zadania.

Jak powstaje status

db.save() działa w transakcji: najpierw kasuje zaznaczone wiersze (z kaskadą w pamięci, _rows_to_vanish, żeby walidacja nie szukała warunków skasowanego progu), potem zapisuje zadanie, wiersze tabel i wymagania, a dopiero gdy nie ma problemów, rusza zasoby (cięcie PNG dotyka dysku, który nie cofa się z transakcją). Zwraca słownik {edited, deleted, described}, czyli to, co się naprawdę zmieniło w porównaniu z bazą.

db.decide() zamienia akcję na status. Jeden przycisk „Zatwierdź” daje approved, gdy nic nie zmieniono teraz, wcześniej w tej rundzie (edited_before w adresie po dodaniu wiersza) ani kiedykolwiek (was_corrected z dziennika); inaczej corrected. Statusu nie da się przekłamać deklaracją. Wpis w correction_event niesie started_at (z formularza, przycięty do „teraz”), finished_at (zegar bazy, LEAST(…, now())), fields_changed, actor i model. refresh_document_status() ustawia document.ingest_status na parsed / approved / rejected.

Więzy bazy zostają ostre, a komunikaty nie: _friendly() tłumaczy UniqueViolation na criterion na zdanie o dwóch progach z tą samą punktacją. Po błędzie formularz wraca z tym, co człowiek wpisał (_overlay), ze statusem 422.

MathJSON

normalizacja w Pythonie, parsowanie w Node

normalize.py → convert.mjs → fill.py

ingest/mathjson/ · task mathjson, zależności przez task mathjson:setup

Bez MathJSON-a silnik w A3 porównywałby stringi, więc 2(x+1) i 2x+2 byłyby dwiema odpowiedziami. Zakres to wyłącznie condition_expression; odpowiedzi zadań zamkniętych to litery BD/FP, gdzie MathJSON nic nie wnosi.

normalize.to_latex(expression) → (latex, None) albo (None, powód)

  1. Cyfry w indeksie górnym (²) na ^{2}, NFKC.
  2. Ucięcie polskiego ogona do pierwszego spójnika (TAIL: lub, albo, oraz, gdzie, jeżeli, przy, dla, i, „, np”) i czasownikowego wstępu (LEAD: zapisanie, obliczenie, wyznaczenie …).
  3. Odmowa przy pierwiastku (√), bo zasięg nie jest odtworzony.
  4. Mapowanie operatorów CKE: ⋅ ∙ · → \cdot, ∶ (U+2236) i : → \div, wszystkie myślniki → -, ≈ ≤ ≥ ≠, π, ∘.
  5. Nawiasy klamrowe dla ^(…), _(…) i pojedynczych indeksów; przecinek dziesiętny na kropkę; ułamki liniowe a/b na \frac{a}{b} w pętli do skutku (obsługuje 1/2/3). Litera jako człon ułamka musi stać samotnie, żeby 60 min/40 min nie rozpadło się na mi + n/40.
  6. Odmowa, gdy zostało słowo prozy (prose_word: ≥ 3 litery, nie jednostka jak km, cm, min, zł). Bez tego „zapisanie P=15” weszłoby jako iloczyn dziewięciu symboli: MathJSON poprawny i bezwartościowy.

convert.mjs

Czyta NDJSON ze stdin ({"id", "latex"}), woła engine.parse(latex, { canonical: false }) z @cortex-js/compute-engine i oddaje {"id", "mathjson"} albo {"id", "error"}. Compute Engine nie rzuca, tylko wstawia węzeł ["Error", …] w drzewo, stąd findError(). Postać niekanoniczna, bo ekran ma pokazać to, co napisał klucz; kanonizację robi konsument w A3.

Parser

Zobacz strukturę jednego klucza bez bazy

uv run python -m parsers.omap_e8.parser "<ścieżka do zasady.pdf>"              # nagłówek + wszystkie zadania
uv run python -m parsers.omap_e8.parser "<ścieżka>" --zadanie 17               # jedno zadanie: progi, warunki, zapisy, odpowiedzi

Pierwsze linie mówią, który dialekt wykryto, jakie reżimy i formy, oraz ostrzeżenia (UWAGA:). Zły dialekt to zły komplet regexów i wszystko poniżej będzie krzywe; wtedy patrz na wykryj_dialekt() i paginę.

Kryterium ma śmieci albo brakuje warunku

  1. Wydrukuj tekst zadania tak, jak widzi go _parsuj_zadanie: page_text dla stron zadania (numer strony jest w podglądzie), poszukaj „Zasady oceniania”, „Rozwiązanie – wersja”, „Przykładowe rozwiązania”. Granica kryteriów to wcześniejszy z tych nagłówków.
  2. Sprawdź separator: w e8-2019 alternatywa to LUB lub lub w osobnej linii, od 2020 tylko LUB. Spójnik w środku zdania celowo nie tnie.
  3. Zapis równoważny zaczyna się po „np.”; jeśli w kluczu jest „np” bez kropki, zapis zostanie w warunku.
  4. Powtarzalny błąd w wielu kluczach naprawia się w parserze, potem task parser:snapshot -- --baseline … pokazuje, które klucze się ruszyły. Reguła G2.3.2: błąd cichy (wygląda poprawnie, np. 12/3 zamiast 1 2/3) idzie do kodu; błąd widoczny może zostać korekcie.

Wymagania podstawy puste lub cudze

Tabela musi mieć „Wymagani” w pierwszych 5 wierszach (WIERSZE_NAGLOWKA) i leżeć pod nagłówkiem zadania. Ostrzeżenie „tabele wymagań sparowane kolejnością” znaczy, że nagłówków w układzie strony było mniej niż zadań; obejrzyj _heading_positions(page) dla tej strony. p.tables[i].rows pokaże, czy pdfplumber w ogóle rozpoznał siatkę.

Ekran korekty

Serwer

Uruchamiaj w swoim terminalu, nie w tle innego procesu. --reload restartuje po zmianie kodu, logi uvicorna pokazują każde żądanie ze statusem. Odpowiedź 422 to walidacja formularza (komunikaty na stronie), 403 to Sec-Fetch-Site (żądanie spoza ekranu), 404 z tekstem to brak strony lub pliku, 500 to prawdziwy błąd w logu.

Strona klucza się nie pokazuje

  • „to zadanie nie ma zapisanej strony w kluczu”: task.page jest NULL (klucz wczytany z arkuszami przed migracją 0004). Przeładuj.
  • „brak pliku w mirrorze”: MIRROR_ROOT wskazuje w złe miejsce, document.path jest względne wobec niego.
  • Stara wersja obrazu po zmianie skali lub pliku: skasuj cache data/cache/pages/. Klucz cache to skrót ścieżki, numer strony, skala i flaga siatki.

LLM: prefill, describe, frame, verify

Zanim zapłacisz

  • LlmUnavailable z komunikatem po polsku mówi wprost: brak klucza w .env, model bez dostawcy, nieznany model, brak adaptera wsadu. Kod wyjścia 2, zero wywołań.
  • Zawsze najpierw dry-run na jednym roczniku: task verify -- --year 2025 --variant 100 (bez --apply) i task frame -- --variant 100. Raport i .json obok pokazują werdykty i powody bez zapisu.
  • --limit 1 na próbę promptu; koszt jednego zadania verify z obrazami to ok. $0,02.

Czytanie wyników

  • Sekcja POWODY w raporcie verify: ten sam powód w wielu zadaniach to błąd parsera. Napraw w kodzie, przeładuj klucze, powtórz dry-run.
  • .json obok raportu ma pełne reasons per zadanie (data/reports/verify-*.json, frame-*.json).
  • unsure: zadanie zostaje pending, powody widać w ekranie nad formularzem i w dzienniku: SELECT * FROM correction_event WHERE action = 'unsure'. Powód zaczynający się od „zapis odrzucony przez walidację lub więz bazy” znaczy, że rekord modelu nie przeszedł przez db.save; więzu nie luzujemy, zadanie idzie do ręki.
  • NIEUDANE w raporcie: wyjątek sieci, odmowa modelu, odpowiedź poza schematem (parsing_error) albo ucięcie na limicie tokenów (finish_reason). Modele myślące liczą rozumowanie do limitu, stąd MAX_OUTPUT_TOKENS 16000 w prefill i verify.

Wsad (--batch)

Konsola wypisuje wsad batch_…: wysłany i stan co 30 s. Po 6 h albo Ctrl-C wsad żyje dalej po stronie API pod tym identyfikatorem; dziś nie ma polecenia „odbierz stary wsad”, więc wynik trzeba pobrać ręcznie w konsoli dostawcy albo puścić przebieg ponownie. Odpowiedzi są zapisywane dopiero po zebraniu całego wsadu.

Podpowiedzi prefillu nie widać w ekranie

SELECT task_id, model, created_at, jsonb_pretty(payload) FROM prefill_suggestion WHERE task_id = 3401;

Ekran pokazuje tylko różnice względem rekordu (differences()). Gdy model i parser zgadzają się co do progów i warunków, listy podpowiedzi nie ma i to jest poprawne.

Słownik pojęć

jedno tłumaczenie, to samo w kodzie, schemacie i dokumentach

klucz (marking scheme)
PDF „zasady oceniania” CKE. Źródło kryteriów, odpowiedzi wzorcowych, rozwiązań przykładowych, wymagań podstawy i reguł. Jeden klucz obsługuje wiele form arkusza.
zeszyt / arkusz (paper)
PDF z treścią zadań, które widzi uczeń. Źródło task_version.content i rysunków. Od 2024 r. nazywa się „zeszyt zadań”.
forma arkusza (exam form)
Kod + wariant + wersja + sesja, np. OMAP-100-X w sesji 2025-05-14. Nie plik; plik jest nośnikiem.
wariant (variant)
Dostosowanie: 100 bazowy, 200/400/500 dostosowania, 700/800 inne, łatwiejsze zadania na to samo wymaganie, C00/K00/Q00 wersje językowe i inne.
wersja (version)
Bliźniaki X i Y: inna treść i inne odpowiedzi w zadaniach zamkniętych, te same kryteria i wymagania.
dialekt
Zestaw regexów nagłówków jednego układu dokumentu: e8-2019, e8-2020, matura, matura-2015. Mierzony z tekstu, nie z nazwy.
reżim wymagań (regime)
Która podstawa programowa lub wymagania egzaminacyjne obowiązują: pp2012, pp2017, pp2024, wym2021 itd. Rozpoznawany z podpisu tabeli i z numeru Dziennika Ustaw w przypisie.
próg / warunek / zapis
Trzy poziomy kryteriów: criterion (ile punktów), criterion_condition (alternatywa warunków), condition_expression (równoważne zapisy tego samego warunku, np. wzory).
reguła przekrojowa (rule)
„Uwagi ogólne” klucza, obowiązujące zakres zadań, stosowane po ocenie kryteriów.
zasób (asset)
Rysunek, wykres lub diagram zadania: ścieżka PNG w blobie, strona i ramka bbox w punktach PDF od lewego górnego rogu, opis alt-text ze statusem.
korpus
Widok corpus_task: zadania approved i corrected, niezależnie od tego, czy rozstrzygnął człowiek, czy model.
S6 / S7 / S8
Pomiary alfy: S6 czy podpowiedź modelu przyspiesza korektę; S7 odsetek opisów rysunków przyjętych bez poprawki; S8 koszt półautomatu (mediana czasu × zadania). W planie A2-auto: S6′ zgodność modelu z próbką ludzką, S8′ dolary na zadanie i odsetek unsure.
G2.x, X1–X7
Numery zadań z planów: G2.1 ekran korekty, G2.3 parser i regresja, G2.4 regiony i wycinki, G2.5 LLM, G2.6 MathJSON, G2.7 raport; X1–X7 to klocki planu A2-auto (migracja 0009, verify, frame, opisy auto, golden set, raporty, decyzje).
